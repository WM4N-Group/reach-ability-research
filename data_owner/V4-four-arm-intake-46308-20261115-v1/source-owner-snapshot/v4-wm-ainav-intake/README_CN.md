# V4四组对比：用户已明确的2×2设计

## 四组

| 组 | 原有规划路线 | 我们新增优化 |
|---|---|---|
| A | VLM＋WM | 关闭 |
| B | VLM＋WM | 开启 |
| C | AINav | 关闭 |
| D | AINav | 开启 |

AINav本身可能使用VLM、技能树和重规划，必须保留这些原有能力；“不加优化”不等于关闭基线原生规划或硬编码路线。D不能未经约定再加WM；A/B的WM调用域与版本相同。B/D仅通过共享优化模块处理候选目标、顺序、准备／退出与后继可执行性，两者共享实现与缺失值语义，不能一个用规则另一个用oracle还称同一消融。

主要比较B−A和D−C，回答新增优化在每条路线是否有效；A−C及B−D只作不同整体路线的比较，不能归因为单独WM效果。首轮每组一次是DEV机制检查，不能从单次胜负声称统计或泛化优势。

## 共同实验条件

采用用户确认V4推箱搭阶场景：三地面箱操作、C箱对接0.60m高台、CLIMB上0.20m箱顶并跨0.40m高差、高台停稳。两段爬升是几何预期，尚无本布局动态资格。原技能、候选控制域、公开输入、目标／支撑／成功与安全门、VLM版本和预算、相机对四组一致；优化计算和额外模型调用如无法完全配平，另报等预算与实际开销，不能藏开销。

基线的WM输出只能用于实际支持的动作／端点；现7a6记录只支持有限PUSH raw响应，不可将其当成功Finish／CLIMB／整链成本。此缺口对A/B一致处理：未支持明确UNKNOWN，禁止读取真实未来或伪造WM预测。若WM在本场景根本没有实际可消费候选，A/B不具备所称方法身份，不能假装跑了四组。

首轮四个独立新main各一次，各自必要zero／lease／watchdog。执行顺序与资源预算由Data在结果前冻结；当前bulk／已closed旧T不修改、不复开。失败和资源/API截断全部保留，不删失败录像、不按结果重试。不能将此前API0 greedy/multistep两组重新命名为本四组。

- 原T public_planner_binding明确VLM_calls=0，是Reach API0路径；本次必须另版本接真实VLM与WM，不能仅改报告标签。

- Data仍唯一物理owner；当前四组派发0、原片0，不声称已入队或跨聊天通知。
